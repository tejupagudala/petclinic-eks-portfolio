## Q1: "Why did you make your EKS API endpoint private-only? What did you give up?"

**Round 1 — 2026-05-20 — Score: 7.5/10**

**What Sai got right:**
- ✅ Defense-in-depth concept correctly applied (network + IAM as separate layers)
- ✅ Acknowledged IAM strictness alongside network controls
- ✅ Named the three threats: DDoS, CVE exploitation, stolen-credential abuse
- ✅ Correct mechanism (private interface endpoint, VPC-only traffic)
- ✅ Clearly articulated the tradeoff (GitHub-hosted runners couldn't reach private endpoint)
- ✅ End-to-end resolution story (built self-hosted runner with IP-locked SG)
- ✅ Mentioned cost tradeoff

**What to fix to reach 9+/10:**
- Explicitly name **"Defense in Depth"** (not just imply the concept)
- Cite real anchors: **CVE-2018-1002105** (K8s API server auth bypass) + **Capital One 2019 breach** (SSRF + IMDSv1 example)
- Clarify cost framing: EKS private endpoint = free; SSM VPC endpoints = $24/mo (what was removed)
- Mention `endpoint_public_access = var.public_endpoint_enabled` is configurable (for bootstrap)
- Add technical details on self-hosted runner: PAT in SSM SecureString, IMDSv2 required, encrypted EBS

**Ideal answer (~90 seconds spoken):**

> *"I made the EKS API endpoint private-only as a defense-in-depth measure. Even with strict IAM — scoping cluster actions to Describe, List, UpdateNodegroupConfig with no Delete — there are attack vectors network controls catch that IAM doesn't.*
>
> *Three categories: First, DDoS — anyone on the public internet could hammer the kube-apiserver. Second, CVE exploitation — the API server has had auth-bypass CVEs like CVE-2018-1002105 that allowed unauthorized privilege escalation; a public endpoint exposes me to those even with perfect IAM. Third, stolen-credential abuse — the Capital One 2019 breach is the canonical example: credentials exfiltrated via SSRF, then used from the public internet. Strict IAM didn't save them because the credentials were used from outside the network.*
>
> *What I gave up: GitHub-hosted runners live on the public internet, so they couldn't reach my private endpoint anymore. That broke my CI/CD. I built the bridge — a self-hosted GitHub Actions runner on EC2 inside the VPC, with a security group locked to my IP via GitHub Secrets. PAT in SSM Parameter Store as SecureString, IMDSv2 required, encrypted EBS, auto-registering via user data.*
>
> *I also evaluated adding VPC interface endpoints for SSM so the runner could pull its PAT fully internally — but three endpoints at ~$8 each would have been $24/month, blowing my $20 budget. So I accepted the runner in a public subnet with egress to internet for SSM. Documented tradeoff: cost over isolation for portfolio scope. In a regulated production environment, I'd budget for the endpoints."*

|---|---|---|
| 1. Network | "Can you even REACH the API endpoint?" | **Phase 3** (private endpoint) |
| 2. Identity / Authentication | "Who are you?" | EKS Access Entries, OIDC, IAM |
| 3. Authorization (IAM + RBAC) | "What are you allowed to do?" | Phase 2 IAM + EKS RBAC |
| 4. Audit | "What did you actually do?" | CloudTrail + K8s audit logs |

**Secret weapon phrases:**
- *"Defense-in-depth — network perimeter AND identity controls"*
- *"CVE-2018-1002105 — K8s API server auth bypass"*
- *"Capital One 2019 breach — strict IAM didn't save them"*
- *"PAT in SSM Parameter Store SecureString, IMDSv2 required"*
- *"In a regulated production environment, I'd budget for the endpoints"*

**Likely hostile follow-ups:**

## Q3: "How is your runner authenticated to GitHub? Walk me through the PAT lifecycle"

**Round 1 — 2026-05-20 — Score: 6/10**
**Round 2 — 2026-05-21 — Score: 8/10** 🔒

**What Sai got right:**
- ✅ PAT in SSM Parameter Store as SecureString
- ✅ EC2 fetches via IAM role (no static credentials)
- ✅ PAT is used to get a registration token
- ✅ Registration token registers the runner
- ✅ ABAC + Role tag mentioned

**What costs the 4 points:**
- ❌ Answered Q2 again (end-to-end runner) instead of focusing on PAT lifecycle
- ❌ Missed PAT creation step (human creates on GitHub.com with `repo` scope)
- ❌ Missed the WHY of the 2-step dance (blast radius — reg token short-lived, PAT long-lived)
- ❌ Missed rotation strategy
- ❌ Missed what to do if PAT leaks
- ❌ Missed IAM role's narrow scope (single SSM parameter ARN, not all SSM)
- ❌ Missed modern upgrade path (GitHub Apps with JWT)

**Ideal answer (~90 seconds spoken):**

> *"The PAT lifecycle has five phases: creation, storage, retrieval, usage, and rotation.*
>
> *Creation: A human creates the PAT on GitHub.com with `repo` scope — that's the permission needed to register a runner at the repo level. The PAT value is captured in my Terraform variable `github_runner_pat`.*
>
> *Storage: Terraform writes it to SSM Parameter Store as a SecureString — encrypted at rest with KMS. The IAM role on the runner EC2 has a single permission: `ssm:GetParameter` on this one specific parameter ARN. Least privilege at the secret level.*
>
> *Retrieval: When the runner boots, its user data script calls SSM via the EC2's instance role — no static AWS credentials, just IMDSv2-protected role assumption. The PAT comes back decrypted.*
>
> *Usage — and this is the senior pattern — the runner does NOT use the PAT to register directly. Instead, it does a 2-step auth dance: use the PAT to call GitHub's API and get a short-lived registration token, then use THAT registration token to register the runner. The registration token expires in about an hour. The runner forgets the PAT entirely after that step. The PAT never lives on the runner's disk past the initial registration.*
>
> *Why the 2-step dance: blast radius. If the runner is compromised after registration, the attacker only finds a long-expired registration token — useless. The PAT itself stays in SSM, protected.*
>
> *Rotation: I create a new PAT on GitHub, update my Terraform variable, run apply — SSM gets the new value. Existing runners are unaffected because they don't hold the PAT. Then I revoke the old PAT on GitHub. If a PAT is suspected leaked, the recovery is: revoke immediately on GitHub, generate new PAT, update SSM, audit GitHub audit log for unauthorized actions.*
>
> *The modern upgrade path is GitHub Apps — they use short-lived JWTs instead of long-lived PATs. I'd move to that for production scale."*

**The 5-Phase PAT Lifecycle (memorize this framing):**
| Phase | What happens | Where |
|---|---|---|
| 1. Creation | Human creates PAT with `repo` scope on GitHub.com | GitHub UI |
| 2. Storage | Terraform writes to SSM Parameter Store as SecureString | AWS SSM |
| 3. Retrieval | EC2 fetches via IAM role (`ssm:GetParameter`) | EC2 boot, user data |
| 4. Usage | PAT → registration token → register runner. PAT forgotten. | One-time at boot |
| 5. Rotation | New PAT on GitHub → update Terraform var → apply → revoke old | When needed |

**Secret weapon phrases:**
- *"5-phase PAT lifecycle: creation, storage, retrieval, usage, rotation"*
- *"2-step auth dance — PAT gets reg token, reg token registers runner"*
- *"The PAT never lives on the runner's disk past initial registration"*
- *"Blast radius: post-registration compromise yields an expired reg token, not the PAT"*
- *"Modern upgrade path: GitHub Apps with short-lived JWTs"*

**Likely hostile follow-ups:**
- *"How would you detect a leaked PAT?"* → GitHub audit log + CloudTrail on SSM Parameter access
- *"Could you use IAM Identity Center instead?"* → For human auth yes; for runner auth, OIDC federation is the modern pattern
- *"What scopes does the PAT need exactly?"* → `repo` for repo-level runners, `admin:org` for org-level
- *"What if your Terraform state file leaks?"* → State is encrypted in S3 backend; PAT in state IS sensitive, which is why you'd switch to GitHub Apps

**Ideal answer (~90 seconds spoken):**

> *"Helm installs the third-party platform pieces in my bootstrap — AWS Load Balancer Controller, and kube-prometheus-stack for observability. Without these, the cluster has no ingress and no metrics.*
>
> *Helm-in-CI is genuinely hard because Helm's state model — releases, secrets, lockfiles in the `kube-system` namespace — assumes a long-running interactive session where a human can intervene. CI runs are atomic and short-lived; they must succeed or fail definitively. A hung Helm install = stuck CI job = blocked PR for hours.*
>
> *I had about 8 commits between March 17-20 chasing this. The four fixes that landed:*
>
> *First, preflight: `helm repo update` before any install, so the local index is always fresh — avoids "chart not found" errors after the upstream repo moves.*
>
> *Second, concurrency control: `cancel-in-progress: true` on the workflow, so re-pushing to a branch kills stale runs instead of queuing them — prevents two installs from racing on the same release name.*
>
> *Third, stale release lockfile cleanup: if a previous run crashed mid-install, Helm leaves a lockfile that blocks the next install. I added a `helm uninstall` step with `|| true` to clean up before retrying.*
>
> *Fourth, proper timeout flags: `--timeout 10m` so Helm fails fast instead of waiting indefinitely. Without this, a hung install would hang the entire workflow.*
>
> *Closing thought: the modern alternative is Argo CD's Helm support — it manages releases declaratively via GitOps, which eliminates the CI-runner interaction problem entirely. For my next iteration that's the upgrade path."*

### Q1 Follow-ups (Self-hosted runner architecture)

**Q1.F1: "How would an attacker reach your runner's IP?"**
> *"Three vectors. One — port scanning at the IP level: blocked by SG locked to my IP only via GitHub Secrets. Two — DNS enumeration: runner has no DNS A record, only IP-addressable. Three — supply chain: compromise a runner registration step. Egress is required for runner registration to GitHub's hosted endpoints; outbound HTTPS only. The IP itself becomes a target only if leaked; portfolio uses dynamic IPs that change on instance restart, increasing the cost-per-attack."*

**Q1.F2: "What if your IP changes?"**
> *"Two options. Update the GitHub Secret + re-apply Terraform — manual but reliable, takes ~5 minutes. Or use a stable jump host (a small EC2 in a public subnet with Elastic IP, only port 443 from my home IP, runner SG allows the jump host's SG). Production with team access: a bastion or Tailscale mesh — engineers connect through a stable identity layer, not IP-based. For my portfolio, the SG update workflow handles the 1-2 IP changes per month."*

**Q1.F3: "How do you rotate the PAT?"**
> *"SSM Parameter Store supports versioned secrets. Generate new PAT on GitHub with required scopes, push to SSM Parameter Store as a new version (`aws ssm put-parameter --overwrite`), the runner re-registers on next reboot which pulls the latest version. Production fix: GitHub Apps instead of PAT — JWT-based auth that's auto-rotating, no manual PAT lifecycle. Migration is straightforward: create a GitHub App, install on the repo, switch runner registration to use App JWT instead of PAT."*

**Q1.F4: "What about the Kubernetes API CA cert — how do you trust it from the runner?"**
> *"`aws eks update-kubeconfig` generates a kubeconfig file that includes the cluster CA bundle from EKS — fetched via the AWS API authenticated by the runner's IAM role. The kubeconfig embeds the CA cert as base64; kubectl validates the TLS cert chain against it on every API call. No manual cert management. Rotation is transparent: when EKS rotates the cluster cert (rare), I re-run `aws eks update-kubeconfig` to refresh the kubeconfig. Production: store kubeconfig in `$RUNNER_TEMP` (ephemeral), regenerate per workflow run."*

### Q2 Follow-ups (PAT lifecycle)

**Q2.F1: "How would you detect a leaked PAT?"**
> *"Two-layer detection. GitHub audit log shows every API call made with the PAT — unusual repo access, unfamiliar IPs, unexpected scopes used. Wire to SIEM (Splunk, Datadog) for anomaly detection. CloudTrail on SSM Parameter access shows who fetched the PAT from SSM — if a non-runner principal accesses the parameter, that's a leak indicator. Production fix: GitHub secret scanning + Dependabot alerts catch leaked PATs in public repos automatically; rotate via revoke + new PAT + SSM update."*

**Q2.F2: "Could you use IAM Identity Center instead?"**
> *"For HUMAN authentication, yes — IAM Identity Center (formerly SSO) is the modern way for engineers to assume roles. But for RUNNER authentication (a non-human principal), OIDC federation is the modern pattern. The runner trusts GitHub's OIDC issuer; AWS validates the token; STS returns temporary credentials. No PAT, no SSM, no rotation. Production migration: switch to OIDC federation across all CI jobs; reduces credential management to zero."*

**Q2.F3: "What scopes does the PAT need exactly?"**
> *"For repository-level self-hosted runners: `repo` scope (full control of private repos) — needed to register the runner with the repo. For organization-level runners: `admin:org` scope. Both are over-broad for portfolio scope but match GitHub's minimum required scopes. Production fix: GitHub Apps support finer-grained permissions — `actions: read`, `administration: write` for runner management only, with no repo access."*

**Q2.F4: "What if your Terraform state file leaks?"**
> *"State is encrypted in S3 backend with KMS. Even if the file leaks (S3 bucket misconfig), the contents are encrypted at rest. But PAT IS in state — that's why production switches to OIDC federation: state doesn't contain credentials. Detection: S3 access logs + CloudTrail on the state bucket. Recovery: rotate PAT immediately, audit GitHub audit log for misuse, rotate KMS key if leak indicates broader compromise."*

### Q3 Follow-ups (VPC endpoint cost decision)

**Q3.F1: "What's the data transfer cost component?"**
> *"Interface VPC endpoints charge $0.01/GB processed in addition to the hourly endpoint cost. For SSM Parameter access at portfolio scale (~1 MB/month), data transfer is negligible — cents per month. But for high-volume services like S3 (gigabytes), data transfer is the dominant cost. Production fix: use gateway endpoints for S3 and DynamoDB (free), interface endpoints only for services that lack gateway endpoint support."*

**Q3.F2: "Why not use a NAT Gateway for the SSM traffic?"**
> *"NAT Gateway costs ~$32/month hourly + $0.045/GB processed. For my $20 budget, that single line item blows the budget. Plus NAT routes all internet-bound traffic, not just SSM — broader attack surface. Interface endpoints are scoped: only the specific AWS service is reachable, no general internet egress. For portfolio scale, the runner's egress for GitHub registration uses direct internet (public subnet placement) instead of NAT. Production with private subnets needs NAT or endpoints — pick based on traffic volume."*

**Q3.F3: "How would VPC Flow Logs help you decide?"**
> *"Enable VPC Flow Logs on the runner ENI for 1 week. Filter for outbound traffic to AWS service IPs (e.g., SSM endpoints — 18.x.x.x range). Count bytes. Multiply by $0.01/GB for endpoint cost estimate. Compare to NAT cost ($32/month + $0.045/GB). For my portfolio with ~1 MB SSM traffic/month, endpoints are cheaper. For high-volume scenarios, NAT might win on per-GB economics. Flow Logs give you the data to decide instead of guessing."*

**Q3.F4: "What about gateway endpoints (S3/DynamoDB) — those are free, right?"**
> *"Yes — gateway endpoints are free at the hourly rate and data transfer rate. But only S3 and DynamoDB are available as gateway endpoints. SSM, Secrets Manager, Bedrock, KMS, ECR, etc. — all interface endpoints, all paid. My portfolio doesn't need gateway endpoints because RDS is private-subnet-only via VPC routing, not S3-via-endpoint. Production with heavy S3 traffic: definitely add the gateway endpoint for free egress to S3."*

### Q4 Follow-ups (Helm vs Argo CD)

**Q4.F1: "Why not use `helm install --wait`?"**
> *"`--wait` waits for resources to reach Ready state. Combined with `--timeout 5m`, this gives bounded retry — if pods don't come Ready within 5 minutes, the install fails and CI fails red. My infra-bootstrap uses this pattern for ALB Controller and Argo CD installs. Without `--wait`, Helm returns success as soon as resources are CREATED (not Ready), so downstream steps can run against not-yet-healthy services. `--wait` is the correctness lever."*

**Q4.F2: "What if a webhook fails during install?"**
> *"Validating/mutating webhooks must be available BEFORE Helm install — otherwise the webhook intercepts the install's own resource creation and fails. Preflight check: `kubectl apply --dry-run=server` against a test manifest; if the webhook is broken, it fails fast with a clear error. My ALB Controller bootstrap recovery (commit `c807b8f`) handles this: detect webhook corruption via dry-run, nuke webhook configs + TLS secret + controller deployment, fresh install. Production fix: separate health probe for webhooks before any dependent installs."*

**Q4.F3: "How would you migrate from Helm-in-CI to Argo CD's Helm support?"**
> *"Three-step migration. One — create Argo CD Application CRDs that reference the same Helm charts via the `chart` source type, with the same values. Two — let Argo CD reconcile; verify it matches current cluster state without changes. Three — remove the Helm install steps from CI. Net effect: same Helm charts deployed, but now via GitOps reconciliation instead of CI imperative installs. Rollbacks become `git revert` on the Application spec. For my portfolio Argo CD is installed but not yet managing apps — this migration is the next step."*
